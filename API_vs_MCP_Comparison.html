Traditional API vs MCP Server

Complete comparison for Amex AI Engineer Interview

Aspect Traditional API Old Way MCP Server New Way
What it is A direct HTTP endpoint (REST / gRPC) that returns data when called A wrapper around APIs that exposes them as tools agents can discover and call through a standard protocol
How agent connects Agent calls the URL directly with custom code:
fetch("https://api.amex.com/v2/txn/123")		 Agent calls any tool the same way:
mcpClient.callTool("get_txn", { txnId: "123" })
Discovery Agent must already know the API exists — hardcoded URL, read the docs manually Agent asks "what tools do you have?" — MCP Server returns the full list automatically at runtime
Auth / API keys Agent holds the API key in its own code — keys scattered across codebases MCP Server holds the key in env vars — agent never sees it
Adding a new tool Write custom integration code in every agent that needs it Add one server.tool() call in the MCP Server — all agents see it instantly
When API changes Every agent's integration code breaks — must fix all of them Fix one file (the MCP Server) — agents don't know anything changed
Response format Every API has its own unique response structure — agent must parse each one differently MCP normalizes everything to one format:
{ content: [{ type: "text", text: "..." }] }
Multiple agents Each agent writes its own fetch / axios / headers / error handling — massive duplication All agents use the same MCP client — zero duplicate code
Example call in agent code fetch("https://api.amex.com/v2/txn/123", { headers: { Authorization: "Bearer xyz123secret" }, method: "GET" }) mcpClient.callTool("get_transaction", { txnId: "123" })
Who knows DB/API details The agent knows everything — URL, auth, table schema, error codes, retry logic Only the MCP Server knows — agent just knows the tool name and what parameters to pass
Security API keys scattered across multiple agent codebases — harder to rotate, easier to leak API keys in one place (MCP Server env vars) — rotate once, done
Protocol HTTP/REST, gRPC, GraphQL, SOAP — different for each API JSON-RPC over stdio — same for every MCP connection
Error handling Each agent implements its own retry logic, timeout handling, error parsing for each API MCP Server handles errors internally — returns clean error message to agent
Testing Test each agent's integration with each API separately — N × M test matrix Test MCP Server once — if the tool works, it works for all agents
Deployment API change → redeploy every agent that uses it API change → redeploy only the MCP Server
Best for Direct service-to-service calls where both sides are known and controlled AI agents that need to discover and use tools dynamically

Code Comparison: Same Task, Two Approaches

Agent needs to get transaction location for fraud check

Traditional API — Agent Code (fraud-agent.ts)
// Agent knows EVERYTHING about the API
// URL, auth, headers, response format, error handling

async function getTransactionLocation(txnId: string) {
  const response = await fetch(
    `https://api.internal.amex.com/v2/transactions/${txnId}`,
    {
      method: "GET",
      headers: {
        "Authorization": `Bearer ${process.env.TXN_API_KEY}`,
        "Content-Type": "application/json",
        "X-Request-ID": uuid(),
        "X-Client-Name": "fraud-agent",
      },
    }
  );

  // Handle errors manually
  if (!response.ok) {
    if (response.status === 429) {
      await sleep(1000);
      return getTransactionLocation(txnId); // retry
    }
    if (response.status === 404) {
      throw new Error("Transaction not found");
    }
    throw new Error(`API error: ${response.status}`);
  }

  // Parse this specific API's response format
  const data = await response.json();

  // Dig into nested response structure
  return {
    city: data.transaction.merchant.location.city,
    country: data.transaction.merchant.location.country,
    lat: data.transaction.merchant.location.coordinates.lat,
    lng: data.transaction.merchant.location.coordinates.lng,
  };
}

// 40+ lines of code
// Agent knows: URL, auth, headers, response shape
// If API changes response format → this code breaks
// If Account Agent needs same data → write this AGAIN
MCP — Agent Code (fraud-agent.ts)
// Agent knows NOTHING about the API
// Just the tool name and parameters

const result = await mcpClient.callTool(
  "get_transaction_location",
  { txnId: "TXN-A8F3K2M9P1Q4" }
);

// That's it. 4 lines.
// Agent doesn't know: URL, auth, headers, DB schema
// If API changes → MCP Server handles it
// If Account Agent needs same data → same 4 lines




// ─────────────────────────────────────────────
// All the complexity lives in the MCP Server:
// File: mcp-servers/transaction-server.ts
// ─────────────────────────────────────────────

server.tool(
  "get_transaction_location",
  "Get city and country of a transaction",
  { txnId: z.string() },
  async ({ txnId }) => {
    // API plumbing lives HERE, not in the agent
    const res = await fetch(`https://api.internal.amex.com/v2/transactions/${txnId}`, {
      headers: { "Authorization": `Bearer ${process.env.TXN_API_KEY}` },
    });
    const data = await res.json();
    return {
      content: [{ type: "text", text: JSON.stringify({
        city: data.transaction.merchant.location.city,
        country: data.transaction.merchant.location.country,
      }) }],
    };
  }
);

Complete Flow: Agent → MCP Server → Database

AGENT (fraud-agent.ts) MCP SERVER (transaction-server.ts) DATABASE (PostgreSQL) "I need transaction location" │ │ calls: callTool("get_transaction_location", { txnId: "TXN-123" }) │ │ ─── MCP protocol (JSON-RPC) ───→ receives { txnId: "TXN-123" } │ │ runs server.tool() handler │ │ executes: db.query( │ "SELECT city, country FROM transactions WHERE id = $1", │ ["TXN-123"] │ ) │ │ ─── SQL over TLS ───→ SELECT city, country │ FROM transactions │ WHERE id = 'TXN-123' │ │ ←──────────────────── { city: "NYC", country: "US" } │ │ ←── MCP response ────────────── wraps result in MCP format: │ { content: [{ type: "text", │ text: '{"city":"NYC","country":"US"}' }] } │ Observes: "Transaction was in NYC" Thinks: "Customer lives in Toronto — mismatch!"

Interview One-Liner

"A Traditional API requires custom integration code in every agent — the agent must know the URL, auth headers, response format, and error handling for each API it calls. MCP standardizes this — you wrap the API once in an MCP Server with server.tool(), and every agent discovers and calls it through the same protocol. It's the difference between N × M custom integrations versus one standard interface."
